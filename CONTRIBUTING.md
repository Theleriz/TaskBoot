# Правила работы с проектом

## Главное правило: `main` всегда рабочий

Ветка `main` в любой момент должна собираться, проходить все проверки и работать без заметных ошибок. Из неё в любой момент можно выпустить версию. Всё, что ещё не готово или не проверено, живёт в отдельной ветке.

Из этого следуют правила ниже. Они относятся ко всем, кто меняет проект: к людям и к AI-агентам.

## Главный разработчик

Решения по проекту принимает главный разработчик. Список может дополняться, например другими учётными записями того же разработчика.

## Как вносить изменения

1. **Отдельная ветка на каждую задачу**, от свежего `main`: `feature/<что-делаем>`, `fix/<что-чиним>`, `docs/<что-описываем>`.
2. **Перед каждым коммитом** — проверки локально:
   - веб: `cd web` → `npm run check` (типы, линтер, форматирование, тесты);
   - если затронуты зависимости — `node tools/third-party-notices.mjs`;
   - если затронута оболочка Windows или сборка — `win32\build.cmd`.
3. **Проверить вручную то, что изменилось**: запустить приложение (`npm run dev` или собранную оболочку) и пройти затронутые сценарии, а также соседние, которые могли задеть изменения.
4. **Pull request в `main`** — только после всех проверок (для новых функций — после бета-этапа, см. ниже). В описании — что изменено и как проверено.
5. **Слияние — только при зелёном CI** (`.github/workflows/ci.yml`: веб-проверки, сборка Windows, актуальность `THIRD_PARTY_NOTICES.md`). Красный CI не «чинят потом» — его чинят до слияния.

## Новые функции: бета в отдельной ветке

Новая функция не попадает в `main`, пока не прошла бета-этап в своей ветке:

1. Функция разрабатывается в ветке `feature/<название>`.
2. Когда она готова к проверке, из этой ветки выпускается предварительная версия — тег с суффиксом, например `v2.1.0-beta.1` (номер — по [docs/versioning.md](docs/versioning.md)). Workflow выпуска публикует её на GitHub как pre-release; в `main` она при этом не попадает.
3. Бета проверяется: CI, ручная проверка в браузере и в приложении для Windows, работа со старыми данными. Найденные ошибки исправляются в той же ветке и выходят следующей бетой (`-beta.2` …) или кандидатом (`-rc.1`).
4. Только после того, как все проверки пройдены, открывается pull request в `main`. После слияния выходит обычная версия (`v2.1.0`) уже из `main`.

Исправления ошибок и мелкие доработки (ветки `fix/…`, `docs/…`) идут обычным путём — проверки и pull request, без бета-этапа, если главный разработчик не решит иначе.

## Работа с `main` напрямую — только в исключениях

Коммиты и push прямо в `main`, в обход pull request, разрешены только в двух случаях:

1. **Форс-мажор с безопасностью**, который нужно исправить прямо сейчас, без вариантов: в репозиторий утекли токены, ключи, пароли или другие секреты; в открытом виде оказались чувствительные данные пользователей. Порядок действий — раздел «Если секрет утёк» в [docs/secrets-policy.md](docs/secrets-policy.md): сначала отозвать или сменить секрет, затем убрать его из репозитория.
   AI-агент, заметивший такую ситуацию, может сам предложить исправить её прямо в `main`, объяснив, что именно утекло. Само исправление делается после согласия главного разработчика.
2. **Главный разработчик** (список выше) может работать с `main` напрямую, когда считает это нужным.

Даже в этих случаях `main` должен оставаться рабочим: проверки из раздела «Как вносить изменения» выполняются, насколько позволяет срочность, а после исправления CI на `main` должен быть зелёным.

## Качество

- **Исправление ошибки — вместе с тестом**, который падал до исправления и проходит после. Так ошибка не вернётся.
- **Новая функция — с тестами** на основные сценарии и на граничные случаи (пустые значения, неверный ввод, старые данные).
- **Данные пользователя не теряются**: изменение формата хранения — только через новую версию схемы и миграцию (`web/src/data/schema.ts`) с тестом на чтение старых данных.
- **Не отключать проверки**, чтобы пройти CI: не пропускать тесты, не ослаблять правила линтера и TypeScript без отдельного обсуждения.
- **Предупреждения — тоже ошибки**: в оболочке Windows они уже превращаются в ошибки сборки; в вебе линтер должен проходить без замечаний.

## Если `main` всё-таки сломался

1. Это главный приоритет: новые изменения в `main` не вливаются, пока он не починен.
2. Если исправление не очевидно за короткое время — откатить проблемный коммит (`git revert`) и чинить спокойно в ветке.
3. В исправление добавить тест, который ловит эту ошибку.

## Выпуски

- Обычные версии (`vA.B.C`) выпускаются только из `main` и только с зелёным CI на этом коммите.
- Предварительные версии (`vA.B.C-beta.N`, `vA.B.C-rc.N`) выпускаются из веток функций и публикуются как pre-release.
- Номер версии выбирается по [docs/versioning.md](docs/versioning.md).

## Прочие правила

- Секреты и контекст AI-агентов не попадают в репозиторий — [docs/secrets-policy.md](docs/secrets-policy.md).
- Новые зависимости — по правилам D-01…D-06 базового ТЗ (раздел 4.1).
- Устройство проекта и как добавлять функции — [docs/architecture.md](docs/architecture.md).

## Защита ветки на GitHub

Правила выше поддерживаются автоматически: для `main` включён ruleset «Protect main» (Settings → Rules → Rulesets):

- изменения попадают в `main` только через pull request;
- слияние возможно, только когда обе проверки CI зелёные: `Web app (types, lint, format, tests, build)` и `Windows shell (build and package)`;
- ветка pull request должна быть актуальной относительно `main` (кнопка «Update branch» на странице PR), чтобы проверки шли на том коде, который получится после слияния;
- `main` нельзя удалить или переписать его историю (force push).

Обход (Bypass list) выдан роли администратора репозитория — в личном репозитории это главный разработчик. Так сохраняется исключение из раздела «Работа с `main` напрямую». AI-агенты, работающие через учётную запись главного разработчика, технически тоже попадают под обход, поэтому для них действуют правила этого документа, а не только настройки GitHub.

Влитые ветки pull request удаляются автоматически. Включены оповещения Dependabot об уязвимостях и автоматические PR с исправлениями.
